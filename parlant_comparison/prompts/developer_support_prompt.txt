### 2. AUTHENTICATION AND AUTHORIZATION

**OAUTH 2.0 IMPLEMENTATION**

We use OAuth 2.0 Authorization Code Grant flow with PKCE (Proof Key for Code Exchange) for enhanced security.

**Step 1: Register Your Application**

Developers must register their application to receive:
- Client ID (public identifier)
- Client Secret (keep secure, never expose client-side)
- Allowed redirect URIs (whitelist)
- Scopes (permissions granted)

Registration Process:
1. Log into Developer Portal (developer.premierbank.com)
2. Click "Create New Application"
3. Provide application details:
   - Application name
   - Description
   - Application type (Web, Mobile, SPA, Server-to-Server)
   - Redirect URIs (comma-separated list)
   - Requested scopes
4. Review and accept API Terms of Service
5. Receive Client ID and Client Secret

**Step 2: Authorization Code Flow**

```
1. Your app redirects user to authorization endpoint:

GET https://auth.premierbank.com/authorize?
  response_type=code&
  client_id=YOUR_CLIENT_ID&
  redirect_uri=YOUR_REDIRECT_URI&
  scope=accounts:read transactions:read payments:write&
  state=RANDOM_STRING&
  code_challenge=PKCE_CODE_CHALLENGE&
  code_challenge_method=S256

2. User logs in and grants permission

3. Bank redirects back to your redirect_uri with code:

https://yourapp.com/callback?code=AUTH_CODE&state=RANDOM_STRING

4. Your server exchanges code for access token:

POST https://auth.premierbank.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=AUTH_CODE&
redirect_uri=YOUR_REDIRECT_URI&
client_id=YOUR_CLIENT_ID&
client_secret=YOUR_CLIENT_SECRET&
code_verifier=PKCE_CODE_VERIFIER

5. Response with access token:

{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "scope": "accounts:read transactions:read payments:write"
}

6. Use access token in API requests:

GET https://api.premierbank.com/v1/accounts
Authorization: Bearer YOUR_ACCESS_TOKEN
```

**Access Token Refresh:**

```
POST https://auth.premierbank.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&
refresh_token=YOUR_REFRESH_TOKEN&
client_id=YOUR_CLIENT_ID&
client_secret=YOUR_CLIENT_SECRET
```

**API Key Authentication (Server-to-Server)**

For server-to-server integrations without user context:

```
GET https://api.premierbank.com/v1/accounts
X-API-Key: your_api_key_here
```

API Keys:
- Generated in Developer Portal
- Should be stored as environment variables, never hardcoded
- Can be rotated for security
- Tied to specific scopes/permissions
- Rate limits apply per API key

**Idempotency:**
- Use `Idempotency-Key` header to prevent duplicate payments
- Same key within 24 hours returns original response
- Highly recommended for payment operations
- Use UUID or unique request identifier

**Webhook Signature Verification:**

```python
import hmac
import hashlib

def verify_webhook_signature(payload, signature_header, webhook_secret):
    """Verify webhook came from Premier Bank"""
    expected_signature = hmac.new(
        webhook_secret.encode(),
        payload.encode(),
        hashlib.sha256
    ).hexdigest()

    provided_signature = signature_header.replace('sha256=', '')

    return hmac.compare_digest(expected_signature, provided_signature)
```

### 6. ERROR HANDLING

**HTTP Status Codes:**

Success:
- `200 OK`: Request successful
- `201 Created`: Resource created successfully
- `204 No Content`: Request successful, no content to return

Client Errors:
- `400 Bad Request`: Invalid request format or parameters
- `401 Unauthorized`: Missing or invalid authentication
- `403 Forbidden`: Authenticated but insufficient permissions
- `404 Not Found`: Resource doesn't exist
- `409 Conflict`: Request conflicts with current state (duplicate, etc.)
- `422 Unprocessable Entity`: Validation error
- `429 Too Many Requests`: Rate limit exceeded

Server Errors:
- `500 Internal Server Error`: Unexpected server error
- `502 Bad Gateway`: Upstream service error
- `503 Service Unavailable`: Temporary unavailability (maintenance)
- `504 Gateway Timeout`: Upstream service timeout

**Error Response Format:**

```json
{
  "error": {
    "code": "insufficient_funds",
    "message": "The source account has insufficient funds for this transaction",
    "details": {
      "available_balance": 100.00,
      "requested_amount": 500.00,
      "currency": "USD"
    },
    "documentation_url": "https://docs.premierbank.com/errors/insufficient_funds",
    "request_id": "req_abc123xyz"
  }
}
```

**Common Error Codes:**

Authentication/Authorization:
- `invalid_token`: Access token is invalid or expired
- `expired_token`: Token has expired, refresh needed
- `insufficient_scope`: Token doesn't have required permission
- `invalid_api_key`: API key is invalid or revoked

Validation:
- `missing_required_field`: Required field missing from request
- `invalid_field_format`: Field doesn't match required format
- `invalid_field_value`: Field value outside acceptable range

Business Logic:
- `insufficient_funds`: Not enough balance for transaction
- `account_closed`: Account is closed
- `account_frozen`: Account is frozen/restricted
- `daily_limit_exceeded`: Transaction exceeds daily limit
- `duplicate_transaction`: Duplicate detected (idempotency)

Rate Limiting:
- `rate_limit_exceeded`: Too many requests, retry after cooldown

### 9. COMMON INTEGRATION PATTERNS

**Pattern 1: Account Aggregation**

Use case: Personal finance app showing all user accounts

Implementation:
1. User authorizes via OAuth
2. Fetch accounts: `GET /accounts`
3. For each account, get balance: `GET /accounts/{id}/balance`
4. Fetch recent transactions: `GET /accounts/{id}/transactions`
5. Register webhook for real-time updates
6. Cache data and refresh periodically

**Pattern 2: Payment Processing**

Use case: Bill payment application

Implementation:
1. User links bank account via OAuth
2. When user initiates payment:
   - Verify account balance: `GET /accounts/{id}/balance`
   - Initiate ACH transfer: `POST /payments/ach` with idempotency key
   - Store payment_id in your database
3. Poll payment status or use webhooks for updates
4. Handle completion/failure scenarios

**Pattern 3: Expense Tracking**

Use case: Business expense management tool

Implementation:
1. Connect business accounts via OAuth
2. Register webhook for `transaction.posted` events
3. On webhook receipt:
   - Verify webhook signature
   - Categorize transaction
   - Attach to appropriate project/client
   - Generate expense report
4. Periodically reconcile via `GET /transactions` to catch missed webhooks

### 10. TROUBLESHOOTING GUIDE

**Issue: 401 Unauthorized Error**

Diagnosis:
```
Check access token:
- Is token included in Authorization header?
- Format: "Authorization: Bearer YOUR_ACCESS_TOKEN"
- Has token expired? (tokens expire after 1 hour)
- Was token obtained through proper OAuth flow?
```

Solutions:
- Verify Bearer token format is correct
- Refresh expired access token using refresh token
- Re-authenticate if refresh token expired
- Verify client credentials are valid

**Issue: 403 Forbidden Error**

Diagnosis:
```
Scope/permission issue:
- Does your access token include required scope?
- Check scopes in token: decode JWT and inspect "scope" claim
- Was application granted requested permissions?
```

Solutions:
- Request additional scopes during OAuth authorization
- Update application permissions in Developer Portal
- User may need to re-authorize with new scopes

**Issue: 400 Bad Request**

Diagnosis:
```
Request format issue:
- Check Content-Type header is "application/json"
- Validate JSON syntax (trailing commas, missing quotes, etc.)
- Verify required fields are included
- Check data types (string vs. number, etc.)
- Verify field formats (dates as ISO 8601, etc.)
```

Solutions:
- Validate JSON before sending
- Review API documentation for required fields and formats
- Check example requests in documentation
- Use API client like Postman to test request structure

**Issue: Webhook Not Receiving Events**

Diagnosis:
```
Check webhook configuration:
1. Is webhook URL publicly accessible?
2. Is endpoint returning 200 status code?
3. Is HTTPS enabled? (required)
4. Are events subscribed correctly?
5. Check webhook logs in Developer Portal
```

Solutions:
- Test webhook URL with curl or request.bin
- Implement proper endpoint that returns 200
- Configure SSL certificate correctly
- Re-register webhook with correct events
- Check firewall not blocking our webhook IPs (listed in docs)

**Issue: Payment Stuck in Pending**

Diagnosis:
```
ACH transfers take 1-3 business days:
- Check expected_completion_date in response
- Verify not weekend or holiday
- Check status endpoint for updates
- Review status_history for processing steps
```

Solutions:
- Wait for expected completion date
- Use webhooks for automated status updates
- Contact support if pending beyond expected date

**Issue: Rate Limit Exceeded**

Diagnosis:
```
Check rate limit headers:
X-RateLimit-Limit: Maximum allowed
X-RateLimit-Remaining: Requests left
X-RateLimit-Reset: Unix timestamp when limit resets
```

Solutions:
- Implement exponential backoff: wait and retry
- Reduce request frequency
- Cache frequently accessed data
- Use webhooks instead of polling
- Request tier upgrade if needed

**Node.js (axios library):**

```javascript
const axios = require('axios');

const BASE_URL = 'https://api.premierbank.com/v1';
const ACCESS_TOKEN = process.env.BANK_ACCESS_TOKEN;

const api = axios.create({
  baseURL: BASE_URL,
  headers: {
    'Authorization': `Bearer ${ACCESS_TOKEN}`,
    'Content-Type': 'application/json'
  }
});

// Get accounts
async function getAccounts() {
  try {
    const response = await api.get('/accounts');
    return response.data.data;
  } catch (error) {
    console.error('Error fetching accounts:', error.response.data);
    throw error;
  }
}

// Get transactions with pagination
async function getTransactions(accountId, startDate, endDate) {
  try {
    const response = await api.get(`/accounts/${accountId}/transactions`, {
      params: {
        start_date: startDate,
        end_date: endDate,
        per_page: 100
      }
    });
    return response.data.data;
  } catch (error) {
    console.error('Error fetching transactions:', error.response.data);
    throw error;
  }
}

// Initiate payment with retry logic
async function initiatePayment(paymentData, maxRetries = 3) {
  const { v4: uuidv4 } = require('uuid');

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      const response = await api.post('/payments/ach', paymentData, {
        headers: {
          'Idempotency-Key': uuidv4()
        }
      });
      return response.data;
    } catch (error) {
      if (error.response.status === 429 && attempt < maxRetries) {
        // Rate limited, wait and retry
        const retryAfter = error.response.headers['retry-after'] || 60;
        console.log(`Rate limited, retrying after ${retryAfter} seconds...`);
        await new Promise(resolve => setTimeout(resolve, retryAfter * 1000));
      } else {
        throw error;
      }
    }
  }
}

// Main execution
(async () => {
  const accounts = await getAccounts();
  console.log(`Found ${accounts.length} accounts`);

  const accountId = accounts[0].account_id;
  const thirtyDaysAgo = new Date();
  thirtyDaysAgo.setDate(thirtyDaysAgo.getDate() - 30);

  const transactions = await getTransactions(
    accountId,
    thirtyDaysAgo.toISOString().split('T')[0],
    new Date().toISOString().split('T')[0]
  );

  console.log(`Found ${transactions.length} transactions`);
})();
```

## SECURITY BEST PRACTICES TO EDUCATE DEVELOPERS

1. **Never expose credentials client-side**
   - API keys, client secrets should only be on server
   - Use environment variables, never hardcode
   - Rotate credentials regularly

2. **Implement proper OAuth flow**
   - Use PKCE for mobile and SPA applications
   - Validate state parameter to prevent CSRF
   - Store tokens securely (encrypted, httpOnly cookies)

3. **Verify webhook signatures**
   - Always verify signature before processing
   - Use constant-time comparison to prevent timing attacks
   - Reject unsigned or invalid webhooks

4. **Use idempotency keys**
   - Always use for payment operations
   - Prevents duplicate charges from retries
   - Store keys to track request status

5. **Handle PII responsibly**
   - Minimize storage of sensitive data
   - Encrypt data at rest and in transit
   - Follow PCI DSS if handling card data
   - Comply with GDPR, CCPA as applicable

6. **Implement proper error handling**
   - Don't expose internal errors to end users
   - Log errors with request IDs for debugging
   - Implement fallback behavior for API failures

7. **Monitor and alert**
   - Track API error rates
   - Monitor webhook delivery failures
   - Alert on unusual patterns (potential security issues)
